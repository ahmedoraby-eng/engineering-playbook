# 06 — Agent identity and attribution

AI agents that write code are teammates with their own names, not ghosts inside a human's account. Every commit says who made it, so a reviewer, the audit trail and Jira's development panel can tell "Malek did this" from "Ahmed did this".

## Rules
1. **An agent commits under its own identity**: `<Name> (Basita AI) <name@agent-domain>`, as both author and committer. Use `scripts/agent-git <agent> commit ...`, which sets the identity for that one command and adds the trailers.
2. **Trailers on every agent commit:**
   ```
   Agent: Malek
   Requested-by: Ahmed Oraby <ahmed.oraby@icloud.com>
   Agent-Model: claude-opus-5-5        (optional)
   Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>
   ```
3. **Issue key** in the branch name or PR title (`DFP-123-short-name`), so Jira links the work.
4. **No Jira Smart Commit commands** (`#done`, `#comment`, `#time`) in agent commits. Jira changes go through the team's approval rules, not through commit messages.
5. **Pull requests opened under a human's account** that contain agent commits carry an `Agent: <Name>` line in the description.
6. Where an agent has its own GitHub App, it pushes and opens pull requests with that app's short-lived installation token, so the push and the pull request are attributed too.

## GitHub as the agent (BASITA-149)
Malek, Haya and Salma each have a GitHub App (`basita-<agent>`); Yousef has the machine user `basita-yousef`, so he can be a pull request's reviewer. `config/github-identities.json` holds their ids and nothing secret. The secrets are in the Keychain, account `basita`: `basita-gh-<agent>-app` (the App's private key, base64 of the PEM on one line), `basita-gh-yousef` (fine-grained: pull requests read and write, contents read, for `basitasolutions`) and `basita-gh-yousef-public` (classic, `public_repo` only, for the public playbook on `ahmedoraby-eng`, where he is not a collaborator).

- **Commits.** `scripts/agent-git <agent> commit` uses the bot's address, `<bot id>+basita-<agent>[bot]@users.noreply.github.com`, so GitHub links the commit to `basita-<agent>[bot]`; the trailers stay. Agents without an App keep `<agent>@<agent-domain>`.
- **Pushes.** `scripts/agent-git <agent> push [remote] [branch]` asks GitHub for a 1-hour installation token for that one repository with `contents:write`, and gives it to that one `git push` through a credential helper that replaces every other one and answers only `https://github.com`, so the Mac's own GitHub login is never used. The remote must have exactly one push URL, and submodules are never pushed (`push.recurseSubmodules=no`). It refuses a push to `main` or `master`, or to a `claude/*` branch (basita-ops `sync.sh` merges those into `main` by itself), `--force`, `+refspec`, deleting a branch, `--mirror`, `--all` and tags. Without a branch it pushes the current one, by name.
- **gh.** `scripts/agent-gh <agent> <gh args>` runs one gh command with `GH_TOKEN` set for that process only. An App's token is revoked (`DELETE /installation/token`) as soon as the command ends, even when it failed, so it never lives on for the rest of its hour. Trace variables that could log it (`GIT_TRACE*`, `GIT_CURL_VERBOSE`, `GH_DEBUG`) and `GIT_CONFIG_*` are cleared. Reads get a read-only token; `pr create|edit|comment|review|ready`, `issue comment` (on pull requests only: the Apps have no issues permission) and a short list of `gh api` writes get `pull_requests:write` with `contents:read`, which cannot merge or push. Yousef, a reviewer, gets reads, `pr review`, `pr comment` and `issue comment` only. It refuses `pr merge|close|reopen`, `gh auth`, secrets, variables, rulesets, workflows, any delete, settings, GraphQL mutations, an App approving a pull request (in any spelling), retargeting a pull request (`pr edit --base`, or `base` in the API), a labels, state, base or event field read from a file, and the labels only Ahmed sets (`reviewed-by-ahmed`, `human-reviewed`, and `jira-status-waived`, which lets a PR past elbayoumy's Jira status check, BASITA-168). Yousef's token is picked by the repository's owner. A token is only minted for an installation listed in the config, so an App installed somewhere else is never used. `AGENT_GH_DRY_RUN=1` shows what would run.
- **Check.** `scripts/gh-check [agent]` is read-only: for each identity the login, the App's permissions (they must be exactly the entry's own `permissions`, or the config's `app_permissions`, so no Workflows), the bot id, that no webhook is configured, every installation (an unlisted one is an `attention` line for Ahmed), the repos each one reaches, and the expiry of Yousef's tokens, with an `attention` line 14 days before; it fails if he has push anywhere, which on the playbook would mean he was made a collaborator. Its own tokens are revoked when it's done. It never prints a token. The hourly check in basita-ops runs it once a day.
- **Storing a secret.** Copy the key or token, then run `scripts/gh-store <agent>` (an App key; or `--file <path to the .pem>`), or `scripts/gh-store yousef basitasolutions|ahmedoraby-eng` for his tokens. Only a private key, a `github_pat_` or a `ghp_` value of the right kind is stored, and nothing is printed. The value goes to `security -i` on stdin, so it never shows in the process list. Clear the clipboard (`pbcopy </dev/null`) and run `scripts/gh-check <agent>`.
- **Workflows (D4).** The Apps have no Workflows permission, so GitHub itself refuses an App's push that changes `.github/workflows/`. Such a change is pushed by Ahmed, or by an agent with his one-time OK.

## Every agent's own identity (BASITA-157)
Nothing goes to GitHub through Ahmed's account (plan section 10). The config also lists the Apps `basita-talia`, `basita-sherif`, `basita-adam`, `basita-nora`, `basita-yousef-docs`, `basita-sync` and `basita-reader`. Each App entry has its own `permissions` (or the top-level `app_permissions` when it has none, as for Malek, Haya and Salma) and a `manifest` (`name`, `public`, `description`) that `scripts/gh-app-new` creates it from. None has Workflows, Administration, Secrets or a write on Actions (D4).

- **Pending.** Until Ahmed creates an App (setup S2), its entry has `app_id`, `client_id` and `bot_id` set to `null` and no installations. `agent-gh` and `agent-git push` refuse it with "not set up yet (Ahmed's setup S2)", before anything is planned or minted. `gh-check` prints `pending <agent>: not created yet`, which is neither FAIL nor attention. Its agent still commits as `<agent>@<agent-domain>`.
- **Branch prefix.** An App with a `branch_prefix` pushes only to branches that start with it, matched exactly: `malek/`, `haya/`, `salma/`, `talia/`, `sherif/`, `adam/`, `nora/`, and `yousef/` for `basita-yousef-docs`. Name branches `<agent>/<KEY>-short-name`. A push to any other branch is refused. `main`, `master` and `claude/*` stay refused for every App.
- **sync.** `basita-sync` (`updates_main`) pushes only `main` of `basitasolutions/basita-ops`, from `sync.sh` on the Mac. Any other repository or branch is refused, and so are a forced push (`--force*`, `+refspec`), deleting, tags and bulk pushes. A push that isn't forced is a fast-forward, which may be a merge commit on top of `main`; GitHub refuses anything else. It runs no `gh` command. It has no Issues permission until D22 is decided.
- **reader.** `basita-reader` (`read_only`) reads only. `agent-gh reader` runs the read commands with a token that carries its own permissions, all `read`: metadata, contents, pull requests, issues, checks, statuses and actions. So `gh pr checks` works too. Every write and every push is refused. Its token is minted with read permissions only, even if the config were changed to give it a write.
- **reader as git's credential (S5).** `scripts/agent-gh reader credential get` is a git credential helper. It answers only `https://github.com`, mints a read-only token for the one repository in the request's path, and stores nothing (`store` and `erase` do nothing). git doesn't tell a helper whether it fetches or pushes. A push with this token fails because the token carries only read permissions, and GitHub refuses the push. That is the control, not the helper. `agent-git <agent> push` replaces every helper with its own for its one command, so a push never picks up the reader. Talia sets it up at S5:
  ```bash
  git config --global credential.https://github.com.helper ""   # drops gh's and the Keychain's helpers for github.com
  git config --global --add credential.https://github.com.helper "!$HOME/Code/engineering-playbook/scripts/agent-gh reader credential"
  git config --global credential.https://github.com.useHttpPath true   # git sends the repository, so the token is for that one
  ```
  To roll it back, set the helper back to `!gh auth git-credential` (plan 10.7).
- **Yousef.** `basita-yousef` stays a user, for his reviews and comments. His `push_app` is `yousef-docs`: `agent-git yousef push` and `agent-gh yousef pr create|edit` run as `basita-yousef-docs[bot]`, so his user never pushes and can't approve what his own docs App pushed. His commits keep `Agent: Yousef` and use the docs bot's address once the App is set up. The docs App is reached only through `yousef`; `agent-gh yousef-docs ...` is refused. The attribution check maps `basita-yousef-docs[bot]` to Yousef.

These wrappers are a guard, not a seal: every key sits in one Mac's Keychain, reachable from any session there. The token's permissions are the real limit, and the attribution check and review are what keep the rest honest.

## Creating an agent's App (BASITA-158)
`scripts/gh-app-new <agent>` creates the App of an agent the config lists as an App with `"app_id": null` (plan 10.6, D21). It refuses any other agent, and an App that already has an id. It builds GitHub's App manifest from the entry: its name, description and `public` flag (`manifest`), its own `permissions` or else `app_permissions`, no events, and the webhook off (`hook_attributes.active: false`). It refuses Workflows, Administration, Secrets, variables, organisation permissions and Actions write (D4). GitHub only takes a manifest as a form POST, so the script serves one page on `127.0.0.1` that posts it to `https://github.com/organizations/basitasolutions/settings/apps/new` with a random `state`, and opens it in the browser. Ahmed, signed in as an owner, clicks **Create**. GitHub sends the browser back to that local server with a one-time code. A different `state` is refused, and the server takes that one callback and stops, or gives up after 10 minutes. The code is traded once at `POST /app-manifests/{code}/conversions`. The private key goes to the Keychain the way `gh-store` stores one (`basita-gh-<agent>-app`, account `basita`, base64 on one line, through `security -i` on stdin). The key, the client secret and the webhook secret are then dropped. The script prints only the App id, client id, bot id and page, the lines to add to the config, and the install link, and the browser goes on to GitHub's install page. Ahmed clicks **Install** and picks the repositories. `scripts/gh-check <agent>` then shows each installation's id for the config. Nothing secret touches disk, the screen or a process's arguments. `--dry-run` prints the manifest and the URL, and neither listens nor opens anything. If the Keychain refuses the key, GitHub still has the App: generate a new private key in its settings and store it with `scripts/gh-store <agent>`.

## Jira and Confluence as the agent (trial)
The cloud id defaults to Basita's site (`basitasolutions.atlassian.net`), so `atl` needs no environment setup in an autonomous session; `ATL_CLOUD_ID` or `--cloud-id` override it.

The read commands print JSON and change nothing: `scripts/atl <agent> jira-get <KEY>` (an issue with its comments, sub-tasks and linked issues) and `jira-jql "<JQL>"`. Each result says `read_by`, the agent whose token answered. A pickup worker gets its context as files from `jira-pickup.sh` and uses these only for what that snapshot did not anticipate, because the Atlassian MCP tools are locked on its routine. `scripts/atl <agent> confluence-get <page id or URL>` and `confluence-search "<words or CQL>"` read Confluence, and `confluence-create <space key> "text" --title "Title"` and `confluence-edit <page id or URL> "text"` write it, each as the agent. Nothing in `atl` deletes.

A Confluence token (`basita-atl-<agent>-confluence`) is a scoped token for the Confluence app with exactly these scopes: `read:page:confluence`, `read:space:confluence`, `read:comment:confluence`, `read:attachment:confluence`, `read:hierarchical-content:confluence`, `write:page:confluence`, `search:confluence` and `read:content-details:confluence` (the search endpoint lists the last two as alternatives). `delete:page:confluence` is left out on purpose.

`scripts/atl <agent> jira-comment <KEY> "text"` and `scripts/atl <agent> confluence-append <page id> "text"` write through the Atlassian gateway with the agent's own **scoped API token**, read from the macOS Keychain at each call: `basita-atl-<agent>-jira` or `basita-atl-<agent>-confluence` (a scoped token covers one app), falling back to `basita-atl-<agent>`; account `basita`. The token is kept only in memory and never printed. Give each token the scopes below and no others, with the longest expiry Atlassian allows (Ahmed, 31/10/2026). A Jira token (`basita-atl-<agent>-jira`) has `read:jira-work`, `write:jira-work` and `write:comment:jira`; a Confluence token has the eight listed above. Store it from the clipboard, not at the prompt: `security add-generic-password -w` at its interactive prompt cuts a token at 128 characters, and Atlassian scoped tokens are longer, so a token stored that way fails with 401. Copy the token, then run the command below. It stores only a value that starts with `ATATT` and has no spaces, so a wrong paste is refused rather than stored, and it keeps the token out of chat, files and shell history. Clear the clipboard afterwards (`pbcopy </dev/null`). Then run `scripts/atl-check <agent> jira` or `scripts/atl-check <agent> confluence`, which checks the stored value's shape without printing it and reads as the agent.

In a comment (Ahmed, 01/11/2026), `@Malek` asks for a reply or action, `FYI @Malek` is information only, and `CC @Malek` means look if you have a concern, with no action asked. A name with no `@` means nothing. `atl` makes each `@Name` of someone with a Jira seat a real mention, and the comment relay counts only the first kind as a request. Ask with `@Name` once, at the ask (Ahmed, 02/11/2026): `@Salma please check AC1`, never `For Salma:` with no `@` (she isn't told) and never the name twice (`For Ahmed: @Ahmed Oraby`). `scripts/atl <agent> jira-comment <KEY> "text" --mention <account id>` also @mentions a person (repeatable), but in a line of its own at the top, away from the ask, so agents use `@Name` instead, and every Jira comment ends with `— <Agent> (Basita AI)` so readers and the comment relay know it came from an agent. `scripts/atl adam jira-return <KEY> "reason"` (Adam only, only from Refinement) moves an issue to `Ready for Testing` and assigns it to Salma with the reason as a comment (operating model §4.3 item 11). `scripts/atl salma jira-dismiss <KEY> --reason "Not a Bug|Already Fixed|Duplicate|Business Requirement"` (Salma only, only from `In Testing`) moves it to `Closed` (item 12). `jira-start` sends Salma from `Ready for Testing` to `In Testing` and refuses every other agent there; in DFP Salma pulls from nothing else. URLs and `[label](url)` in comments are posted as clickable links (§4.4 item 5). `scripts/atl <agent> jira-create <BASITA|DFP|ELB> <Story|Task|Bug|Sub-task|Epic> "summary" "description" [--parent KEY] [--label L] [--assignee NAME] [--link KEY]` creates an issue and prints its key. The description ends with the agent's signature. Any agent creates a Story, Task, Bug or Sub-task, and a Sub-task needs `--parent`. Nora creates an Epic in any of the three projects, and Sherif in BASITA only. It's unassigned unless Adam, Nora, Sherif or Salma give `--assignee`, with a name from the list in `client.py`. Assigning can start a pickup, under the same gates as any other assignment. A DFP Bug goes to Adam in `Refinement` to validate, from any agent. Only Salma may send a clear technical bug straight to an engineer, with `--assignee malek` or `--assignee haya` and `--link` to the DFP issue it came from: it then moves to `Ready for Development` and takes that issue's unreleased Fix Version, so pickup can start the engineer. Any other assignee is refused (operating model §4.3 item 11). `--link` adds `relates to`. Other types are refused, and so are the labels only Ahmed sets. This works the same in a direct session and in a pickup, on the Mac that holds the Keychain tokens. `scripts/atl maya --via sherif jira-create ...` creates under Sherif's account and signs as Maya. `scripts/atl <agent> jira-flow <KEY> <action> "why"` makes one step of DFP's flow: `submit` (whoever works DFP issues: Malek and Haya, and Nora, Sherif and Maya on DFP work that isn't code (BASITA-147); In Development to Ready for Testing, assigns Salma), `pass` and `fail` (Salma, In Testing to Ready for Acceptance, assigns Adam, or to Ready for Development, assigns whoever last worked it), `accept` and `reject` (Adam, Ready for Acceptance to Ready for Release, assigns Ahmed, or to Ready for Development, assigns whoever last worked it). Any other agent or status is refused. `scripts/atl <agent> jira-ready <KEY> --assignee NAME` moves an issue the agent refined from Refinement to Ready (`Ready for Development` in DFP; standing approval, operating model §4.3 item 9; never an Epic). In DFP `--assignee` is required, can't be Adam or Salma, and the issue needs an unreleased Fix Version, because pickup starts no one without them. Otherwise it stays in Refinement. `scripts/atl <agent> jira-start <KEY>` is an agent's other transition: To Do to In Progress, with the `agent-picked` label (a second pickup is refused) and a comment; it needs `read:jira-work` and `write:jira-work`. Done comes from a merged PR with `Closes <KEY>`; every other transition stays with the human owner.

t="$(pbpaste)"; if [[ "$t" == ATATT* && "$t" != *[[:space:]]* ]]; then security add-generic-password -U -s basita-atl-salma-jira -a basita -w "$t"; else echo "Not a token: nothing stored"; fi; unset t

## Agents with no seat on a product
An agent with no seat on a product works through another agent's user there, with `--via`. Maya has no Jira seat: `scripts/atl maya --via sherif jira-comment DFP-1 "text"` uses Sherif's Jira token and signs `— Maya (Basita AI, via Sherif)`, so Jira shows that account and the signature says who did the work. She has her own Confluence user, so `scripts/atl maya confluence-get <page>` takes no `--via`. An agent with no Atlassian user and no `--via` fails on the missing Keychain item. In git they are ordinary agents: `scripts/agent-git maya commit` commits as `Maya (Basita AI) <maya@<agent-domain>>`.

## Enforcement
`reusable-agent-attribution.yml` checks every pull request: agent commits must carry a matching `Agent:` trailer and no Smart Commit command, unknown authors fail, AI-made commits authored as a human and missing issue keys are warnings. A commit by an agent's App bot (by login, or its noreply address) needs the `Agent:` trailer of that agent, and a pull request opened by a bot must not name, or contain commits of, another agent. The map of bots comes from `config/github-identities.json`; those findings are warnings while its `"attribution"` is `"warn"`, and errors once Ahmed sets `"fail"`. Other bots, such as dependabot, are skipped. On a free private repository GitHub cannot make the check required, so the merge rule ("merge only on green") is the control.

This is attribution, not isolation: agents on one machine can reach each other's identities. Review and the check are what keep it honest.
